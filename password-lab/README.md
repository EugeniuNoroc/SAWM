## п. 2–3. Таблица `user` и уязвимость хранения паролей в открытом виде

До миграции таблица выглядит так:

```
 id | login | password             | email
 1  | admin | admin123             | admin@lab.local
 2  | ivan  | qwerty               | ivan@mail.com
 3  | maria | qwerty               | maria@mail.com
 4  | petr  | 123456               | petr@mail.com
 5  | elena | Kot-Lampa-Reka-2026! | elena@mail.com
 6  | oleg  | r7#Vq!m2Zp@9xL$w     | oleg@mail.com
```

Почему это опасно:

- **Любая утечка БД = утечка всех паролей сразу.** Источники: SQL-инъекция (лаба 1),
  украденный бэкап, доступ админа/разработчика, логи, дамп на тестовом сервере.
- **Повторное использование паролей.** Люди ставят один пароль на почту, банк, соцсети —
  утечка с маленького сайта открывает доступ к чужим аккаунтам везде (credential stuffing).
- **Внутренний нарушитель** видит пароли без всяких атак.
- **Нет «второго рубежа».** При хэшировании злоумышленнику после кражи БД ещё нужно
  подбирать пароли; при открытом тексте — нет.
- **Юридически**: нарушение требований к защите персональных данных (GDPR, закон РМ № 133/2011
  о защите персональных данных).

## п. 4. Как формировать и хранить пароли

**Формирование (рекомендации NIST SP 800-63B):**
- длина важнее «сложности»: минимум 12 символов, лучше 16+; хорошо работают фразы-пароли;
- запрет популярных и уже утёкших паролей (проверка по списку);
- пароль не должен содержать логин, имя, дату рождения;
- уникальный пароль для каждого сервиса → менеджер паролей;
- включать двухфакторную аутентификацию;
- не заставлять менять пароль каждые N дней без причины (люди начинают делать `Pass1`, `Pass2`…).

**Хранение:**
- никогда не хранить пароль и не шифровать его обратимо — только **медленный хэш с солью**:
  Argon2id (первый выбор OWASP), scrypt, bcrypt, PBKDF2 (для FIPS);
- соль — случайная, ≥16 байт, своя для каждого пользователя, из `SecureRandom`;
- сравнение хэшей за постоянное время;
- не писать пароли в логи; передавать только по HTTPS;
- при необходимости — «перец» (pepper): секрет, хранящийся вне БД;
- одинаковое сообщение «Неверный логин или пароль», ограничение числа попыток входа.

**Примеры** (проверены политикой в `PasswordService.checkPolicy`, вывод в `PasswordTest`):

| Пароль | Оценка | Почему |
|---|---|---|
| `123456`, `qwerty` | уязвимый | топ самых популярных, подбирается мгновенно |
| `admin123` | уязвимый | популярный + содержит логин |
| `P@ssw0rd` | уязвимый | замены букв на символы известны всем словарям, короткий |
| `ivan2026!Ivan` | уязвимый | содержит логин и год |
| `Kot-Lampa-Reka-2026!` | надёжный | длинная фраза из случайных слов, легко запомнить |
| `r7#Vq!m2Zp@9xL$w` | надёжный | 16 случайных символов (удобно с менеджером паролей) |
| `зелёный слон пьёт чай у реки` | надёжный | длинная фраза-пароль |

## п. 5. Почему MD5 и SHA-1 считаются уязвимыми

**1. Сломана стойкость к коллизиям** (найти два разных сообщения с одинаковым хэшем):
- MD5: коллизии найдены в 2004 г. (Ван Сяоюнь), сейчас находятся за секунды на ноутбуке;
  в 2008 г. так подделали сертификат центра сертификации, в 2012 г. вирус Flame подделал
  подпись Microsoft.
- SHA-1: первая практическая коллизия — SHAttered (Google + CWI, 2017), в 2020 г. — коллизия
  с выбранным префиксом (SHA-1 is a Shambles), стоимость порядка десятков тысяч долларов.

Поэтому для подписей и сертификатов они запрещены.

**2. Для паролей главная проблема — они слишком быстрые.** MD5/SHA-1 созданы, чтобы быстро
считать контрольные суммы файлов. Одна современная видеокарта считает **десятки миллиардов
MD5 в секунду**, поэтому все 8-символьные пароли перебираются за часы–дни. В демо
`PasswordTest`/`ConsoleDemo` один Argon2id обходится примерно в **30 000 раз дороже** одного MD5
(и требует 19 МиБ памяти на попытку).

**3. Без соли одинаковые пароли дают одинаковый хэш** — это видно на странице `/users`:
у ivan и maria `MD5 = d8578edf8458ce06fbc5bb76a58c5ca4`.

**Какие атаки возможны на пароли, захэшированные MD5** (принципы, без инструкций):
- **Поиск по готовым базам и радужным таблицам (rainbow tables)** — хэши популярных паролей
  посчитаны заранее; `e10adc3949ba59abbe56e057f20f883e` ищется в интернете и сразу даёт `123456`.
- **Словарная атака** — перебор списков паролей из прошлых утечек и их вариаций
  (`qwerty` → `Qwerty1!`).
- **Полный перебор (brute force)** — благодаря скорости MD5 короткие пароли перебираются целиком.
- **Атака по совпадениям** — без соли один подобранный хэш раскрывает пароли всех пользователей
  с таким же хэшем, а по совпадающим хэшам видно, у кого общий пароль.
- Коллизии MD5 сами по себе для паролей вторичны: важна обратная задача (найти пароль по хэшу),
  и её решают перебором именно из-за скорости.

## п. 6–7. Применённая функция: Argon2id

**Почему Argon2id:**
- победитель международного конкурса Password Hashing Competition (2015), стандарт **RFC 9106**;
- первая рекомендация **OWASP Password Storage Cheat Sheet**;
- **memory-hard**: каждая попытка требует много памяти (здесь 19 МиБ) — видеокарты и
  специализированные чипы (ASIC) теряют своё преимущество, массовый параллельный перебор дорог;
- вариант **id** совмещает защиту от атак по сторонним каналам (Argon2i) и от GPU-перебора (Argon2d);
- параметры (память, итерации, потоки) настраиваются и **записываются в сам хэш** — их можно
  увеличивать со временем, не ломая старые записи.

Параметры (минимум OWASP): `m=19456 КиБ, t=2, p=1`, соль 16 байт, хэш 32 байта.
Реализация — BouncyCastle `Argon2BytesGenerator`; совместимость проверена эталонной
библиотекой `argon2-cffi` в обе стороны.

**Как пароли хранятся в БД после миграции** (кнопка «Захэшировать» на `/users`):

```
 login | password
 admin | $argon2id$v=19$m=19456,t=2,p=1$xjM98jEYgla64qYZcxTz+Q$MZTgtsRKypZyQv+BxI4CmPLoiRz9QCGHplCcjFmR/TE
 ivan  | $argon2id$v=19$m=19456,t=2,p=1$h6M3ok2tlAt3b6+Ub3ZDTA$zrk9xGR7qp0mdTroLIJ0jgAntmhvNUfkewMZpEd/MgY
 maria | $argon2id$v=19$m=19456,t=2,p=1$ba5ts6AnNQB/LoCxEPWjqw$BP4W5dbvkVoM7DSyR+NuY+3alvm0DfRQwbHl1ELQrKo
```

Разбор строки: `$argon2id` — алгоритм, `v=19` — версия, `m,t,p` — параметры,
далее **соль** (base64), далее **хэш** (base64).
У ivan и maria пароль один и тот же (`qwerty`), но строки разные — у них разные соли.

**Как работает вход:** из БД берётся строка, из неё — соль и параметры; введённый пароль
хэшируется с ними же; результат сравнивается с сохранённым за постоянное время
(`MessageDigest.isEqual`). Сам пароль нигде не хранится и не восстанавливается.

**Преимущества «скрытого» хранения:**
- при утечке БД злоумышленник получает не пароли, а хэши, которые надо подбирать —
  а с Argon2id это очень дорого; надёжные пароли подобрать практически невозможно;
- администратор и разработчики не видят пароли пользователей;
- пользователи успевают сменить пароли до того, как их подберут;
- выполняются требования стандартов и законодательства о персональных данных.

**Роль соли:**
- одинаковые пароли дают **разные** хэши → по базе не видно, у кого общий пароль;
- **бесполезны радужные таблицы** и готовые базы хэшей: их пришлось бы строить отдельно
  под каждую соль;
- нельзя атаковать всех пользователей сразу: перебор приходится вести **отдельно для каждой
  записи**, стоимость атаки умножается на число пользователей;
- соль не секретна — она хранится рядом с хэшем; её задача — уникальность, а не тайна.
  (Секретное дополнение, хранящееся вне БД, называется «перец», pepper.)
