# Лабораторная работа 2. Методы предотвращения SQL-инъекций (Java)

Мини веб-приложение на **Java (Spring Boot)** с встроенной БД **H2**, которое:
закрытую панель администратора с аутентификацией, форму входа, таблицу `user`
с 7 записями, демонстрацию SQL-инъекции и защиту от неё (client-side +
server-side), а также автоматический тест безопасности.

---

## 1. Как запустить

Требуется JDK 17+ и Maven. В корне проекта:

```bash
mvn spring-boot:run
```

Откройте в браузере: **http://localhost:8080/**

> Внешняя СУБД не нужна — база H2 поднимается в памяти и наполняется
> 7 пользователями автоматически при старте.
> Таблицу можно посмотреть в веб-консоли: http://localhost:8080/h2-console
> (JDBC URL: `jdbc:h2:mem:labdb`, пользователь `sa`, пароль пустой).

Учётные данные для «честного» входа (любая из 7 записей), например:

| login | password |
|-------|-----------|
| admin | Adm1n_P@ss |
| ivanov | qwerty123 |
| manager | Manager#99 |

## 2. Соответствие пунктам задания

**Предварительные условия**

1. Закрытая страница администратора — `GET /admin`
   (`AdminController`): без аутентификации идёт редирект на `/login`.
2. Доступ только через проверку подлинности (сессия `HttpSession`).
3. Форма аутентификации с 2 полями (логин и пароль) — `templates/login.html`.
4. БД с таблицей `user` (id, login, password) — `config/DatabaseInitializer`.

**Требования**

1. **7 записей** создаются в `DatabaseInitializer`.
2. **SQL-инъекция** для входа без правильных данных — см. раздел 3.
3. **Client-side** (`static/js/validation.js`) и **server-side**
   (`util/InputValidator` + `PreparedStatement` в `dao/UserDao`) проверки.
4. **Проверка безопасности** — автотест `src/test/java/com/lab/SecurityTest.java`.

## 3. Демонстрация SQL-инъекции (п.2)

На форме входа переключите режим на **«Уязвимый режим (демо атаки)»** и
введите в поле **Логин** одну из строк, а пароль — любой:

```
admin' --
' OR '1'='1' --
' OR 1=1 --
```

Произойдёт вход в панель администратора **без знания пароля**.

### Почему это работает

Уязвимый метод (`UserDao.authenticateVulnerable`) склеивает ввод в текст SQL:

```java
"SELECT * FROM \"user\" WHERE login = '" + login + "' AND password = '" + password + "'"
```

При вводе `login = ' OR '1'='1' --` запрос превращается в:

```sql
SELECT * FROM "user" WHERE login = '' OR '1'='1' --' AND password = '...'
```

Условие `'1'='1'` всегда истинно, а `--` превращает остаток строки (проверку
пароля) в комментарий. Запрос возвращает строки → приложение считает вход
успешным. Это классическая атака, описанная в
[OWASP Testing for SQL Injection (OTG-INPVAL-005)](https://owasp.org/www-project-web-security-testing-guide/).

## 4. Методы защиты (п.3)

Защита построена по принципу «нескольких рубежей» (defense in depth).

### A. Server-side — параметризованный запрос (главный рубеж)

`UserDao.authenticateSecure` использует `PreparedStatement` (заполнители `?`):

```java
"SELECT COUNT(*) FROM \"user\" WHERE login = ? AND password = ?"
```

Значения передаются как **данные**, а не как часть SQL-кода. СУБД компилирует
запрос заранее, поэтому кавычки, `--`, `OR` внутри ввода трактуются буквально —
изменить логику запроса невозможно. Это основной и достаточный способ защиты.

### B. Server-side — валидация ввода (`InputValidator`)

Принцип «белого списка»: логин/пароль проверяются по разрешающим регулярным
выражениям, а подозрительные на инъекцию фрагменты (`'`, `"`, `--`, `;`,
`UNION`, `SELECT`, `OR 1=1` …) отклоняются. Это дополнительный рубеж.

### C. Client-side — JavaScript-проверка (`validation.js`)

Те же правила выполняются в браузере до отправки формы: пользователь сразу
видит ошибку. **Важно:** клиентскую проверку легко обойти (отключить JS,
отправить запрос через `curl`/Postman), поэтому она не заменяет серверную, а
лишь улучшает удобство и служит первым фильтром.

---

## 5. Проверка безопасности (п.4)

Автоматический тест запускается командой:

```bash
mvn test
```

`SecurityTest` доказывает, что:

1. инъекция **обходит** уязвимый метод (воспроизводит проблему);
2. та же инъекция **не работает** в безопасном методе (`PreparedStatement`);
3. серверный валидатор **отклоняет** вредоносный ввод (5/5 полезных нагрузок);
4. корректные данные по-прежнему принимаются, неверный пароль — отклоняется.

## 7. Замечание о хранении паролей

В этой учебной работе пароли хранятся в открытом виде — строго по схеме задания
(`id, login, password`) и для наглядности. В реальных системах пароли
**обязательно** хранят в виде криптографического хэша (BCrypt, Argon2, scrypt)
с солью, а не как plaintext.
